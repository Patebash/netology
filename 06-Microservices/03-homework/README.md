# Домашнее задание к занятию "Микросервисы: подходы"

*Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры. Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.*

## Задача 1: Обеспечить разработку
> Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.
> Решение должно соответствовать следующим требованиям:
> * облачная система;
> * система контроля версий Git;
> * репозиторий на каждый сервис;
> * запуск сборки по событию из системы контроля версий;
> * запуск сборки по кнопке с указанием параметров;
> * возможность привязать настройки к каждой сборке;
> * возможность создания шаблонов для различных конфигураций сборок;
> * возможность безопасного хранения секретных данных (пароли, ключи доступа);
> * несколько конфигураций для сборки из одного репозитория;
> * кастомные шаги при сборке;
> * собственные докер-образы для сборки проектов;
> * возможность развернуть агентов сборки на собственных серверах;
> * возможность параллельного запуска нескольких сборок;
> * возможность параллельного запуска тестов.
> 
> Обоснуйте свой выбор.

## Ответ:

Для организации процесса разработки предлагается использовать следующий стек:

* **GitLab.com** — хранение исходного кода и управление репозиториями.
* **GitLab CI/CD** — непрерывная интеграция и непрерывная поставка.
* **GitLab Runner** — выполнение сборок на собственных серверах.
* **Docker** — изолированная среда выполнения сборок.
* **HashiCorp Vault** (или встроенные защищённые переменные GitLab) — безопасное хранение секретов.

---

## Архитектура решения

```text
Разработчик
      │
      │ git push / Merge Request
      ▼
 GitLab (облако)
      │
      ▼
 GitLab CI/CD
      │
      ├── GitLab Runner №1
      ├── GitLab Runner №2
      └── GitLab Runner №N
              │
              ▼
        Docker-контейнеры
              │
      Сборка → Тесты → Deploy
```

## Как выполняются требования

### Хранение исходного кода

Каждый микросервис размещается в отдельном Git-репозитории GitLab, что позволяет независимо развивать, тестировать и выпускать сервисы.

---

### Непрерывная интеграция (CI)

После события **Push** или создания **Merge Request** автоматически запускается конвейер (Pipeline), который выполняет:

* сборку проекта;
* статический анализ кода;
* запуск модульных тестов;
* создание Docker-образа;
* публикацию артефактов.

---

### Непрерывная поставка (CD)

После успешной сборки конвейер может автоматически или вручную выполнить:

* публикацию Docker-образа в Registry;
* развёртывание на тестовом окружении;
* развёртывание в продуктивной среде после подтверждения.

---

### Запуск сборки вручную

GitLab позволяет запускать Pipeline вручную через веб-интерфейс с передачей переменных (например, выбор окружения или версии приложения).

---

### Настройки каждой сборки

Конфигурация каждой сборки хранится в файле `.gitlab-ci.yml`, который находится в репозитории проекта. Благодаря этому изменения в процессе сборки версионируются вместе с кодом.

---

### Шаблоны сборок

GitLab поддерживает повторное использование шаблонов (`include`, YAML Anchors, Templates), что позволяет создавать единые стандарты сборки для разных проектов.

---

### Хранение секретов

Пароли, токены и ключи доступа хранятся в защищённых переменных GitLab CI/CD или во внешнем хранилище секретов, например HashiCorp Vault. Значения не попадают в репозиторий и не отображаются в логах.

---

### Несколько конфигураций сборки

Один репозиторий может содержать несколько конвейеров, например:

* сборка Backend;
* сборка Frontend;
* сборка Docker-образа;
* публикация документации.

Запуск нужной конфигурации определяется веткой, тегом, правилами (`rules`) или переменными.

---

### Кастомные шаги

В конвейер можно добавить любые пользовательские команды, например:

* запуск скриптов;
* миграцию базы данных;
* проверку качества кода;
* уведомление в корпоративный чат.

---

### Собственные Docker-образы

Для выполнения сборок можно использовать собственные Docker-образы с заранее установленными зависимостями, что ускоряет выполнение конвейеров и обеспечивает одинаковое окружение.

---

### GitLab Runner

GitLab Runner устанавливается на собственных серверах компании и выполняет сборки, обеспечивая контроль над инфраструктурой и возможность масштабирования.

---

### Параллельное выполнение

GitLab CI/CD поддерживает:

* одновременный запуск нескольких Pipeline;
* параллельное выполнение этапов (`parallel`);
* параллельный запуск тестов на нескольких Runner.

Это сокращает время сборки и ускоряет выпуск новых версий.

---

## Обоснование выбора

В качестве платформы предлагается использовать **GitLab.com** совместно с **GitLab CI/CD** и **GitLab Runner**. Такое решение полностью удовлетворяет всем требованиям задания: предоставляет облачное хранилище Git-репозиториев, поддерживает автоматический и ручной запуск конвейеров, позволяет использовать собственные Docker-образы и шаблоны сборок, безопасно хранить секреты, запускать несколько конфигураций сборки из одного репозитория, выполнять пользовательские шаги, а также разворачивать GitLab Runner на собственных серверах для масштабирования и параллельного выполнения сборок и тестов.

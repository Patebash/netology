# Домашнее задание к занятию "Введение в микросервисы"

## Задание:
> Руководство крупного интернет-магазина, у которого постоянно растёт пользовательская база и количество заказов, рассматривает возможность переделки своей внутренней ИТ-системы на основе микросервисов. Вас пригласили в качестве консультанта для оценки целесообразности перехода на микросервисную архитектуру. Опишите, какие выгоды может получить компания от перехода на микросервисную архитектуру и какие проблемы нужно решить в первую очередь.

## Ответ:

### Возможные выгоды

1. **Независимое масштабирование**

   * Можно увеличивать ресурсы только для наиболее нагруженных сервисов (например, каталог товаров, корзина, оформление заказов), а не для всей системы.
   * Это снижает затраты на инфраструктуру.

2. **Повышение отказоустойчивости**

   * Сбой одного микросервиса не приводит к остановке всего интернет-магазина.
   * Например, при отказе сервиса рекомендаций покупатели смогут продолжить оформлять заказы.

3. **Более быстрое внедрение изменений**

   * Команды могут независимо разрабатывать и обновлять отдельные сервисы.
   * Новые функции появляются быстрее, без необходимости выпускать весь продукт целиком.

4. **Использование разных технологий**

   * Для каждого сервиса можно выбрать наиболее подходящий язык программирования, базу данных или фреймворк.
   * Например, поиск можно реализовать на специализированной поисковой системе, а обработку платежей — на другой платформе.

5. **Удобство сопровождения**

   * Небольшие сервисы проще понимать, тестировать и поддерживать.
   * Проще находить и исправлять ошибки.

6. **Рост производительности команд**

   * Несколько команд могут одновременно работать над разными сервисами практически независимо друг от друга.

---

### Основные проблемы, которые необходимо решить

1. **Определить границы микросервисов**

   * Разделить систему на независимые бизнес-домены:

     * каталог товаров;
     * корзина;
     * оформление заказов;
     * платежи;
     * доставка;
     * пользователи;
     * уведомления.

2. **Организовать взаимодействие между сервисами**

   * Продумать API.
   * Использовать очереди сообщений или брокеры событий для обмена данными.
   * Обеспечить надежность взаимодействия.

3. **Управление данными**

   * Каждый сервис должен владеть собственной базой данных.
   * Нужно решить проблему согласованности данных между сервисами.

4. **Мониторинг и логирование**

   * Настроить централизованный сбор логов.
   * Реализовать мониторинг состояния сервисов.
   * Организовать распределённую трассировку запросов.

5. **Автоматизация развертывания**

   * Настроить CI/CD.
   * Использовать контейнеризацию (например, Docker) и системы оркестрации (например, Kubernetes).

6. **Безопасность**

   * Организовать аутентификацию и авторизацию между сервисами.
   * Защитить API.
   * Обеспечить безопасную передачу данных.

7. **Изменение процессов разработки**

   * Перестроить работу команд.
   * Ввести единые стандарты разработки, тестирования и эксплуатации.

---

### Возможные недостатки перехода

* Повышается сложность архитектуры.
* Увеличивается количество сетевых взаимодействий.
* Становится сложнее тестировать систему целиком.
* Возрастают требования к DevOps-процессам и мониторингу.
* Переход требует значительных временных и финансовых затрат.

---

### Вывод

Для крупного интернет-магазина с быстро растущей нагрузкой переход на микросервисную архитектуру может значительно повысить **масштабируемость, отказоустойчивость и скорость разработки**. Однако успешный переход возможен только при тщательной подготовке: необходимо правильно выделить границы сервисов, организовать их взаимодействие, автоматизировать развертывание, обеспечить мониторинг и безопасность. В большинстве случаев рекомендуется выполнять миграцию **постепенно**, начиная с наиболее независимых и нагруженных компонентов системы, а не переписывать всю систему сразу.

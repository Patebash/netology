# Домашнее задание к занятию "Микросервисы: принципы"

*Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры. Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.*

## Задача 1: API Gateway

> Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.
> Решение должно соответствовать следующим требованиям:
> * маршрутизация запросов к нужному сервису на основе конфигурации,
> * возможность проверки аутентификационной информации в запросах,
> * обеспечение терминации HTTPS.
> 
> Обоснуйте свой выбор.

## Ответ:

### Для реализации API Gateway рассмотрим несколько популярных решений:
* NGINX
* Kong

* HAProxy

---

### Анализ решений

#### NGINX

Преимущества:
* высокая производительность;
* простая настройка;
* поддержка HTTPS;
* балансировка нагрузки;
* широкое распространение.

Недостатки:
* для полноценного API Gateway требуется настройка дополнительных модулей;
* отсутствует встроенная система управления API.

---

#### Kong

Преимущества:
* специально разработан как API Gateway;
* встроенная проверка JWT, OAuth2 и API Key;
* большое количество готовых плагинов;
* удобное масштабирование;
* хорошая интеграция с Kubernetes и Docker.

Недостатки:
* более сложная настройка;
* требует дополнительных компонентов (например, базы данных или работы в DB-less режиме).

---

#### Traefik

Преимущества:
* автоматическое обнаружение сервисов;
* удобная интеграция с Docker и Kubernetes;
* простая настройка сертификатов Let's Encrypt.

Недостатки:
* меньше возможностей по управлению API, чем у Kong;
* часть функций реализуется через middleware.

---

#### HAProxy

Преимущества:
* очень высокая производительность;
* отличная балансировка нагрузки;
* надежность.

Недостатки:
* ориентирован прежде всего на балансировку трафика;
* функции API Gateway реализованы ограниченно.

---

### Выбор решения

Для указанных в задании требований наиболее подходящим является **Kong**.

### Обоснование выбора

Kong полностью соответствует требованиям задания:

* ✅ выполняет маршрутизацию запросов к нужным микросервисам;
* ✅ поддерживает проверку аутентификации (JWT, OAuth2, API Key);
* ✅ обеспечивает HTTPS-терминацию;
* ✅ поддерживает балансировку нагрузки;
* ✅ имеет большое количество готовых плагинов;
* ✅ хорошо масштабируется и подходит для микросервисной архитектуры.

Для организации API Gateway лучше использовать **Kong**, поскольку он обеспечивает все необходимые функции: маршрутизацию запросов, проверку аутентификации, HTTPS-терминацию и дополнительные возможности (балансировка нагрузки, ограничение числа запросов, логирование и мониторинг). Это решение хорошо подходит для эксплуатации крупных микросервисных систем и позволяет упростить дальнейшее развитие инфраструктуры.

## Задача 2: Брокер сообщений

> Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.
> Решение должно соответствовать следующим требованиям:
> * поддержка кластеризации для обеспечения надёжности,
> * хранение сообщений на диске в процессе доставки,
> * высокая скорость работы,
> * поддержка различных форматов сообщений,
> * разделение прав доступа к различным потокам сообщений,
> * простота эксплуатации.
> 
> Обоснуйте свой выбор.

## Ответ:

* RabbitMQ
* Apache Kafka
* Apache ActiveMQ
* NATS

---

### Анализ решений

#### RabbitMQ

Преимущества:

* простая установка и настройка;
* поддержка кластеризации;
* надежное хранение сообщений на диске;
* поддержка различных протоколов (AMQP, MQTT, STOMP);
* развитая система разграничения прав доступа;
* удобный веб-интерфейс администрирования.

Недостатки:

* производительность ниже, чем у Kafka при обработке очень больших потоков данных.

---

#### Apache Kafka

Преимущества:

* очень высокая производительность;
* горизонтальное масштабирование;
* надежное хранение сообщений на диске;
* высокая отказоустойчивость.

Недостатки:

* более сложная эксплуатация;
* изначально ориентирована на потоковую обработку данных, а не на классические очереди сообщений.

---

#### Apache ActiveMQ

Преимущества:

* поддержка большого количества протоколов;
* надежная доставка сообщений;
* поддержка кластеров.

Недостатки:

* уступает RabbitMQ и Kafka по производительности;
* менее популярен в современных микросервисных системах.

---

#### NATS JetStream

Преимущества:

* очень высокая скорость работы;
* простая архитектура;
* поддержка хранения сообщений;
* поддержка кластеризации.

Недостатки:

* меньше возможностей по сравнению с RabbitMQ и Kafka;
* менее распространен в корпоративных проектах.

---

### Выбор решения

Для рассматриваемой системы предлагается использовать **RabbitMQ**.

### Обоснование выбора

RabbitMQ полностью удовлетворяет требованиям задания:

* ✅ поддерживает кластеризацию для обеспечения высокой доступности;
* ✅ обеспечивает хранение сообщений на диске до их доставки получателю;
* ✅ обладает высокой производительностью для большинства корпоративных систем;
* ✅ поддерживает различные форматы сообщений и несколько протоколов обмена;
* ✅ предоставляет гибкую систему разграничения прав доступа (виртуальные хосты, пользователи, роли);
* ✅ отличается простотой установки, эксплуатации и администрирования благодаря удобному веб-интерфейсу.

Для реализации брокера сообщений лучше использовать **RabbitMQ**, поскольку он сочетает высокую надежность, простоту эксплуатации и широкий набор функций, необходимых для обмена сообщениями между микросервисами. Он поддерживает кластеризацию, хранение сообщений на диске, различные форматы сообщений, разграничение прав доступа и обеспечивает высокую производительность при сравнительно простой эксплуатации.
Кроме того, RabbitMQ широко применяется в микросервисных архитектурах и хорошо интегрируется с популярными языками программирования, контейнерными платформами (Docker, Kubernetes) и средствами автоматизации.
